# 旅遊景點候選產生器

當使用者給出地名，並希望取得附近景點或可匯入旅程的 Markdown 時使用本 skill。
本 skill 只產生建議與文字輸出，不直接修改 workspace 中的旅程 Markdown，也不呼叫
Places、Maps、Routes 或其他需要 API key 的 runtime API。

## 工作流程

1. 讀取使用者的地名，以及可選的搜尋範圍與偏好，例如：城市／街區、步行或親子、自然或歷史、預計停留天數。
2. 判斷地名是否足以定位。若同名地點、國家／城市不明，或「附近」的範圍會顯著改變結果，先提出最少量的澄清問題；不要猜測使用者指的是哪一個地點。
3. 使用目前可用的網路搜尋能力查找候選。搜尋時可使用當地語言、日文或英文的地名變體；優先使用官方觀光局、政府、景點管理單位或場館官方頁面，次之才使用可信的旅遊資料作為發現線索。
4. 對每個候選確認名稱、所在區域與可用的地圖搜尋文字。沒有可靠來源支持的地址、開放狀態、交通時間、票價或營業時間，不得補寫或推測。
5. 在使用者確認前，只列出候選，不輸出可匯入 block，也不宣稱已加入旅程。候選清單至少包含：編號、景點名稱、地圖搜尋文字、推薦理由、來源連結；距離或時間只有在來源明確支持時才列出。
6. 使用者以編號或名稱選定候選後，再輸出可直接貼到 `## 備案` 下方的 fenced Markdown block。若使用者沒有指定停留時間，每個景點使用 60 分鐘。
7. 輸出 block 後提醒使用者自行貼入目前旅程的 Markdown；不得自動改檔案、localStorage 或其他旅程資料。

## 候選清單格式

候選清單可以使用下列格式，來源連結必須對應實際查閱過的頁面：

| # | 景點 | 地圖搜尋文字 | 推薦理由 | 官方／查證來源 |
|---|---|---|---|---|
| 1 | 景點名稱 | 可直接交給 Google Maps 的文字 | 與地名或偏好的關聯 | [官方頁面](https://example.com) |

候選排序可考慮與搜尋地名的關聯、使用者偏好、來源可靠性與資訊完整度；不得把排序說成自動最佳化路線。若某個資料無法查證，明確標記「未確認」並從 Markdown 欄位省略，不要製造精確數值。

## Markdown 輸出契約

確認選擇後，只輸出景點 list item（不要在 block 內重複 `## 備案` heading），格式固定為四個欄位：

```md
- 名稱 | 地圖搜尋文字 | 分鐘 | 備註
```

規則：

- 一行一個已確認的景點，順序依使用者選擇順序；不要依距離或營業時間自行重排。
- `名稱` 必填；`地圖搜尋文字` 優先使用查證到的官方名稱／地址，否則使用「景點名稱 + 搜尋地名」，不得虛構地址或座標。
- `分鐘` 必須是整數；使用者未指定時為 `60`。不要從未查證的營業時間推導停留時間。
- `備註` 只放使用者明確要求的偏好或已由來源支持的簡短資訊；未知的交通、營業時間、預約與費用留在候選說明中標為未確認，不要寫入假資料。
- 欄位內容若包含半形 `|`，改用全形 `｜` 或移除，避免破壞本專案四欄 Markdown parser；不要用額外欄位或巢狀表格。
- 不在景點名稱前加 `@HH:MM`，因為這些項目要貼入備案區，備案景點不得帶開始時間。

輸出範例：

```md
- 淺草寺 | 東京都台東区浅草2-3-1 | 60 | 歷史景點
- 隅田公園 | 隅田公園 台東區側 | 90 | 河岸散步
```

## 安全與範圍邊界

- 地名不明確時先澄清，不要用搜尋結果第一筆代替使用者決定。
- 搜尋結果過時、官方頁面無法取得或來源互相矛盾時，保留不確定性並告知使用者；不要把推論寫成事實。
- 不自動查詢或承諾即時交通、營業時間、票價、預約、天氣或路線最佳化。
- 不建立 API key、不新增 server endpoint、不在 React app 中觸發自動搜尋。
- 不直接編輯 `specs/` 以外的旅程資料、不寫入 localStorage、不建立或修改使用者的行程檔案。
