# Feature Specification: 多日旅遊行程編排 Demo

**Feature Branch**: `001-itinerary-planner-demo`

**Created**: 2026-09-17

**Status**: Ready for planning

**Input**: User description: "建立可在本機編排景點備案、多日時間表與 Google Maps 路線的旅遊規劃 demo。"

## Clarifications

### Session 2026-09-17

- Q: 第一版的時間表是否自動排程？ → A: 使用者手填開始時間與停留時間，系統只計算結束時間並提示衝突。
- Q: Google Maps 是否內嵌或預設交通方式？ → A: 不內嵌、不預設交通方式，只產生外部路線連結。
- Q: 第一版管理多少旅程？ → A: 只管理一個可包含多日的旅程，資料保存在目前瀏覽器。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 建立景點備案 (Priority: P1)

作為規劃個人旅程的使用者，我想逐筆輸入景點或貼上 Markdown 清單，先建立尚未排定日期的景點備案，避免在開始排時間前遺漏想去的地方。

**Why this priority**: 沒有可重複編輯的景點備案，就無法進行任何後續行程安排。

**Independent Test**: 在空白旅程中分別用表單及 Markdown 新增景點，確認所有有效景點出現在備案區且可以編輯或刪除。

**Acceptance Scenarios**:

1. **Given** 空白旅程，**When** 使用者輸入景點名稱並新增，**Then** 景點會出現在備案區並帶有 60 分鐘預設停留時間。
2. **Given** Markdown 文字包含多個有效項目，**When** 使用者匯入，**Then** 每個項目依輸入順序加入備案區。
3. **Given** Markdown 中有空白行或格式錯誤的停留時間，**When** 使用者嘗試匯入，**Then** 空白行被忽略、錯誤行保留並顯示行號，其他有效行仍可匯入。
4. **Given** 備案區已有景點，**When** 使用者編輯或刪除該景點，**Then** 清單立即反映變更。

---

### User Story 2 - 編排多日行程 (Priority: P1)

作為使用者，我想建立多個日期，並在備案區與每日行程之間移動、排序景點，以形成符合自己偏好的旅遊順序。

**Why this priority**: 將備案轉成有日期與順序的行程，是產品最核心的使用價值。

**Independent Test**: 建立兩天行程，把四個景點分配到不同日期、重新排序，再把其中一站移回備案區；所有區域必須反映相同且唯一的景點配置。

**Acceptance Scenarios**:

1. **Given** 備案區有四個景點，**When** 使用者建立兩天並將景點移入不同日期，**Then** 每個景點只會出現在一個位置。
2. **Given** 同一天有多個景點，**When** 使用者拖曳或使用替代控制調整順序，**Then** 當日順序依使用者操作更新。
3. **Given** 景點已安排到某一天，**When** 使用者將它移回備案區，**Then** 排程資訊被清除且景點仍保留。
4. **Given** 某一天包含景點，**When** 使用者確認刪除該日，**Then** 該日所有景點返回備案區而不被刪除。

---

### User Story 3 - 設定時間並辨識衝突 (Priority: P2)

作為使用者，我想為已排定的景點輸入開始時間及停留時間，看到預計結束時間與衝突提示，同時保留自行決定順序的權利。

**Why this priority**: 時間資訊讓景點順序成為實際可執行的行程，但不應阻礙早期探索與調整。

**Independent Test**: 為同一天兩個景點設定重疊與不重疊時間，確認結束時間與警告能正確更新，而景點順序不會被系統自動改變。

**Acceptance Scenarios**:

1. **Given** 一個已排定景點，**When** 使用者填入 09:30 與 90 分鐘，**Then** 顯示結束時間 11:00。
2. **Given** 同一天兩個景點的時間區間重疊，**When** 任一時間被更新，**Then** 兩個相關景點顯示非阻斷式衝突提示。
3. **Given** 景點的拖曳順序與開始時間先後不一致，**When** 行程顯示，**Then** 系統提示時間順序異常但不自動重新排序。
4. **Given** 開始時間空白，**When** 使用者保存其他內容，**Then** 景點仍可留在行程中且不產生虛構時間。

---

### User Story 4 - 開啟地圖路線 (Priority: P2)

作為使用者，我想依當日景點順序開啟 Google Maps，以便查看路線並在 Google Maps 中自行選擇交通方式。

**Why this priority**: 路線連結讓手動編排行程能直接銜接實際導航，而不增加外部服務設定成本。

**Independent Test**: 分別使用一站、五站及超過五站的行程產生連結，確認搜尋或分段路線都維持景點順序且沒有遺漏。

**Acceptance Scenarios**:

1. **Given** 某日只有一個景點，**When** 使用者開啟地圖，**Then** 以該景點的地圖搜尋文字開啟搜尋結果。
2. **Given** 某日有二至五個景點，**When** 使用者開啟路線，**Then** 產生一條依拖曳順序排列的路線且不指定交通方式。
3. **Given** 某日景點超過安全單段上限或網址長度上限，**When** 系統產生路線，**Then** 路線被拆成連續多段，下一段起點與上一段終點相同。

### Edge Cases

- 景點名稱只有空白時不得新增。
- Markdown 欄位前後空白不屬於景點內容；同名景點仍視為不同項目。
- 停留時間必須是 1 至 1,440 分鐘的整數；無效值不得覆蓋原有有效值。
- 沒有任何日期或景點時必須顯示可採取下一步的空狀態。
- 只有一個日期時不得刪除最後一天；旅程始終至少保留一天。
- 地圖搜尋文字空白時使用景點名稱；兩者都空白的景點不得存在。
- 瀏覽器資料遺失、版本不相容或內容損毀時，不得造成空白頁面；必須保留原始內容供復原並載入安全的初始旅程。
- 一段地圖網址經編碼後不得超過 2,048 個字元。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供單一旅程，包含旅程名稱、可選的開始日期、至少一天行程與共用備案區。
- **FR-002**: 使用者 MUST 能以名稱、地圖搜尋文字、預設停留分鐘及備註逐筆新增景點；只有名稱必填。
- **FR-003**: 使用者 MUST 能以每行一個項目的 Markdown 清單批次匯入景點。
- **FR-004**: Markdown 每行 MUST 按 `名稱 | 地圖搜尋文字 | 停留分鐘 | 備註` 解讀，允許省略尾端欄位。
- **FR-005**: 地圖搜尋文字省略時 MUST 使用景點名稱；停留時間省略時 MUST 使用 60 分鐘。
- **FR-006**: Markdown 匯入 MUST 忽略空白行，並以行號回報無效行而不阻止其他有效行匯入。
- **FR-007**: 系統 MUST 保留重複名稱的景點，並為每個景點維持獨立身分。
- **FR-008**: 使用者 MUST 能編輯或刪除景點；刪除已排定景點時 MUST 先要求確認。
- **FR-009**: 使用者 MUST 能新增行程日；若旅程有開始日期，新日期 MUST 連續遞增。
- **FR-010**: 旅程 MUST 始終至少保留一天。
- **FR-011**: 使用者 MUST 能將景點在備案區、不同日期及同一天不同位置之間移動。
- **FR-012**: 每個景點在任一時間 MUST 只存在於備案區或一個日期中，不得重複配置。
- **FR-013**: 拖曳 MUST 有鍵盤操作或明確的移動按鈕作為等價替代方案。
- **FR-014**: 刪除含有景點的日期 MUST 先要求確認，確認後 MUST 將景點依原順序返回備案區。
- **FR-015**: 已排定景點 MUST 接受可空白的開始時間及 1 至 1,440 分鐘的停留時間。
- **FR-016**: 系統 MUST 根據開始時間及停留分鐘顯示同日結束時間，不得推算移動時間。
- **FR-017**: 系統 MUST 標示同日時間區間重疊及拖曳順序與時間先後不一致，但 MUST NOT 自動調整順序或時間。
- **FR-018**: 地圖路線 MUST 使用每一天目前的拖曳順序，不得根據時間或距離重新排序。
- **FR-019**: 一站行程 MUST 產生 Google Maps 搜尋連結；多站行程 MUST 產生 Google Maps 路線連結。
- **FR-020**: 地圖連結 MUST NOT 預設交通方式，且 MUST NOT 要求 API key。
- **FR-021**: 每段路線 MUST 最多包含五站且編碼後不得超過 2,048 字元；超出時 MUST 產生共享邊界站點的連續分段連結。
- **FR-022**: 系統 MUST 在每次有效狀態變更後保存整個旅程，並在重新整理後還原內容與順序。
- **FR-023**: 保存資料 MUST 帶有 schema version；無法解析或版本不支援時 MUST 保存原始值作為備份並載入安全初始旅程。
- **FR-024**: UI 與錯誤訊息 MUST 使用繁體中文，且所有互動控制 MUST 有可辨識標籤及鍵盤 focus 狀態。
- **FR-025**: 系統 MUST 在備案、日期與地圖操作不可用時顯示具體空狀態或原因，不得只顯示空白區域。

### Key Entities

- **Trip**: 使用者目前唯一的旅程，包含名稱、可選開始日期、行程日、景點與配置狀態。
- **Place**: 一個候選景點，包含唯一身分、名稱、地圖搜尋文字、備註及預設停留時間。
- **Day Plan**: 旅程中的一天，包含唯一身分、日期或日次標籤，以及景點排列順序。
- **Placement**: 景點目前位於備案或某一天的位置，包含排序、可選開始時間及停留時間。
- **Import Result**: 一次 Markdown 匯入的有效景點與帶行號錯誤，讓使用者能修正失敗項目。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新使用者能在 3 分鐘內輸入四個景點、建立兩天行程並完成分配，過程不需閱讀外部說明。
- **SC-002**: 對最多 50 個景點與 14 天行程的每次新增、編輯、移動及排序，畫面在一般桌面瀏覽器上於 200 毫秒內反映結果。
- **SC-003**: 100% 的有效狀態變更在重新整理後可還原相同景點內容、配置與順序。
- **SC-004**: Markdown parser、時間計算、衝突偵測、狀態轉換及地圖連結的定義案例全部具有自動化驗證。
- **SC-005**: 使用者只用鍵盤或畫面移動控制，即可完成將景點從備案移入某日、重新排序及移回備案的完整流程。
- **SC-006**: 一至十二站的地圖連結驗證中，所有景點皆按使用者順序出現，且沒有單一網址超過 2,048 字元。
- **SC-007**: 儲存內容損毀或版本不支援時，應用程式仍能顯示可操作的初始旅程，且原始內容有可辨識的備份。

## Assumptions

- 第一版供單一使用者在同一瀏覽器及裝置使用，不提供同步或多人編輯。
- 桌面瀏覽器是主要操作環境；窄螢幕必須可閱讀與編輯，但不要求完整觸控拖曳體驗。
- Google Maps 對文字搜尋結果的解析屬於外部行為；本功能只保證產生格式正確、順序正確的連結。
- 使用者自行確認地址、營業時間、交通方式與實際可行性。
- 旅程規模上限以 50 個景點及 14 天作為 MVP 驗證基準，而不是硬性拒絕更多資料。
